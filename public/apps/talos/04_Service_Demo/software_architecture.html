04 Service demo · Software

Software architecture

For the developers: the end-to-end software stack from the FPGA blocks in the payload to the webhook that drops an alert into a customer's common operating picture. The rule from the build-versus-buy analysis is simple — the digital receiver firmware, the geolocation solver, the catalogue and the analytics are the product and are built in-house; flight-software frameworks, mission control, databases and map engines are taken from open source or licensed. Everything is designed so that the same containers run in an EU sovereign cloud and, with no code changes, inside an air-gapped classified enclave.

Principles and the big picture

Five principles shape the stack. Reduce on board, correlate on the ground: raw IQ is 9.6 Gbit/s for the comms path alone, so the satellite emits reports and short snapshots and the ground does the cross-correlation (research 03 §5). Time is a first-class datum: every sample, report and product carries GNSS time to ≤20 ns, because TDOA lives or dies on it. One pipeline, four product levels: L1 detections, L2 geolocations, L3 catalogue, L4 analytics, matching the operators' practice and the products page[R4-29]. Sovereign by construction: no managed service that cannot run on-premises; a one-way path into the enclave. Standards at the edges: GeoJSON and OGC API Features for commercial users, STANAG 4676 tracks and a 4559-style catalogue for NATO — a gap no commercial operator fills today[R4-44].

Flight software

The payload processor is a Zynq UltraScale+ RFSoC class board (the Xiphos Q8RF doubles as digitiser and processor on HawkEye 360's satellites[R2-x82]) with a rad-tolerant supervisor. The ARM cores run a flight-software framework — F´ (JPL) or NASA cFS, both Apache-2.0 with large heritage and no export issue (research 02 §J) — and the programmable logic runs the signal-processing blocks. The bus OBC keeps the vendor's own software; the two talk over CAN/SpaceWire with a small, versioned command and telemetry dictionary.

Ground data platform

Every service is a stateless container that consumes from one message-bus topic and publishes to the next, with the stores as the only state. That makes the pipeline replayable (reprocess a day of L0 with a new detector), horizontally scalable (the CAF solver is the only compute hotspot) and portable into the enclave (the same images, pulled through the diode).

The CAF / TDOA–FDOA solver

The solver computes, for each satellite pair and each candidate emitter, the cross-ambiguity function of the two time-aligned snapshots and finds its peak in delay and Doppler:

$$ A(\tau,\nu)=\int_{0}^{T} s_1(t)\,s_2^{*}(t+\tau)\,e^{-j2\pi\nu t}\,dt ,\qquad (\hat\tau,\hat\nu)=\arg\max_{\tau,\nu}|A(\tau,\nu)| $$

The achievable measurement precision follows from the signal bandwidth \(B\), integration time \(T\) and effective SNR \(\gamma\): \( \sigma_\tau \approx 1/(\beta\sqrt{BT\gamma}) \) and \( \sigma_f \approx 1/(T_e\sqrt{BT\gamma}) \), with \(\beta\) and \(T_e\) the RMS bandwidth and duration (the geolocation theory page derives them and the TDOA/FDOA simulator turns them into ellipses on the map). The solver's job in software terms is to size the snapshot so that these σ values meet the CEP target without blowing the downlink budget — the calculator below uses the same ORB.RF functions the simulator uses.

Catalogue service and the maturity state machine

The catalogue is the product that compounds over time. New fixes are gated against it (position within k·ellipse, class match, parametric distance); non-matches create Candidate instances, matches with drift raise mode change, instances unseen for N expected observation opportunities become dormant. Maturity moves Candidate → Provisional (≥3 consistent geolocations) → Confirmed (corroborated by imagery, AIS/ADS-B or ground truth) → Characterised (stable parametrics, platform assigned) → Archived, and every transition is logged with who or what triggered it, because government customers audit it[R4-28]. The unclassified core never holds ELNOT/ENOT mappings or national platform associations; those live in a classified annex table set in the enclave with the same keys (research 04 §5.3). The entity model (signal class, detection, geolocation, emitter instance, track, pattern-of-life, alert) is specified on the EW database page.

APIs and payloads

Commercial operators deliver GeoJSON over REST and JSON detections with ellipses[R4-13][R4-8]; NATO expects STANAG 4676 tracks and 4559/NSILI libraries[R4-44]. TALOS exposes one gateway with OGC API Features collections per product level, a tasking resource, webhooks and export endpoints. Every response carries classification, release_caveat and provenance; data rights are enforced per customer with row-level security on the AOI subscription, never by filtering in the client.

Console front-end

The operations console demo is the prototype of the production front-end and fixes its information architecture: map with band-coloured emitters and ellipses, a time scrubber as the primary axis, a per-pass spectrum strip, AOI tasking with predicted passes and CEP, a rule-based alert feed and a catalogue browser with maturity levels — the feature set the research derives from Mission Space, Guardian LOCATE, satID and military COPs[R4-29]. The production build replaces the demo's canvas renderer with a vector-tile map engine (MapLibre GL) and nautical/aeronautical basemaps, adds APP-6 symbology as a toggle, reads live data through the OGC API with server-sent events for alerts, and keeps the classification banners, release caveats and audit hooks the demo already shows. It is a TypeScript single-page application with no server-side rendering so that the same bundle can be hosted in the enclave; it must work with keyboard only and pass WCAG 2.1 AA, which matters for the analyst desks of government customers.

Security and accreditation architecture

The threat model is a nation-state adversary interested in what TALOS collects and in the ability to task it (risk T-17 in the risk register). The architecture answers with: identity for every service and user (OIDC, hardware tokens for operators, mutual TLS on the bus); AES-256 for TC/TM and products with keys in an HSM in Greece; signed collection decks and signed flight-software images; an unclassified platform and a classified enclave that run the same containers but are joined only by a one-way diode; row-level data rights; SBOMs and continuous vulnerability scanning; incident reporting and resilience obligations under NIS2 and the proposed EU Space Act[R5-12]; and a Facility Security Clearance with cleared staff for NATO/EU SECRET products, which the EUSPA RFI shows institutional buyers will audit[R4-16]. Export control is enforced in software too: product tiers are tagged, and the gateway refuses to release IQ, parametric libraries or tasking rights to customer identities without the matching licence record (research 05 §3.5).

Deployment

Sovereign cloud (unclassified line)

Kubernetes on an EU provider or a national data centre; PostgreSQL with PostGIS and TimescaleDB for the relational and time-series stores; S3-compatible object storage for L0 and IQ with a WORM tier for provenance; NATS JetStream (or Kafka) as the bus; GPU node pool for the CAF solver; Keycloak for identity; everything deployed from signed images by GitOps. No managed service that lacks an on-premises equivalent is allowed, so the enclave can mirror it.

Classified enclave (government line)

The same Helm charts on an air-gapped cluster inside the cleared facility; MinIO for object storage; images and the daily unclassified product feed arrive through the data diode; outputs go to the MoD COP over an accredited link and to the national EW database as low-classification source records. Cleared analysts work here; the ELNOT annex and national platform associations never leave.

Sizing

Computed from BASELINE.payload (30 GB/day of reduced products per satellite, 2,000 comms and 500 radar snapshots per orbit) and the stage definitions; IQ snapshots dominate storage, so the retention policy (hot 90 days, cold 3 years, exemplars for ever) is the main cost lever.

Observability

Every service emits OpenTelemetry traces keyed by pass_id, so one trace follows a pass from the landing bucket to the alert webhook and the latency budget in the sequence diagram becomes a measured histogram. Service-level objectives are stated as products, not servers: L2 geolocations published within 25 min of LOS for 95 % of passes; alert webhook delivery within 60 s of creation; API availability 99.5 %; catalogue update latency per customer SLA. Pipeline health is watched with per-level counters (frames ingested, detections, measurements, fixes, transitions, alerts) and their ratios — a sudden drop in fixes per detection points to a clock-bias or snapshot problem before any customer notices. Spacecraft telemetry lands in the same TimescaleDB so that payload health (RFSoC temperature, SEU counters, OCXO lock) can be correlated with product quality.

Software-in-the-loop with the orbit engine is the backbone: the collection planner, pass scheduler, geolocation geometry and the console are all exercised against a simulated constellation long before launch, and the same harness later reproduces on-orbit anomalies from telemetry. Replay of recorded IQ is how the detector and classifier are improved without new collections — HawkEye describes a billion-point unclassified database used to train and validate its algorithms[R4-2]; TALOS starts that archive in commissioning.

Team and skills

The software organisation grows with the programme phases in HEADCOUNT: within the 15–22 FTE of Phase B the software and firmware core is about a third; by operations and cluster build (35–50 FTE) the data platform and product teams dominate. The skills that are hard to hire in Greece and should be secured early are FPGA DSP for RFSoC, ELINT-literate algorithm engineers and security engineers with accreditation experience.
